# Murky Aces — архитектура системы врагов

Дата обновления: 2026-11-02.

Статус: **общий фундамент Enemy реализован; существующий дрон переведён на общий lifecycle. Проектирование остальных систем продолжается.** Ниже отмечены выполненные задачи и открытые части плана. Контракты поведения, движения и атаки, а также новые общие системы остаются проектными предложениями.

## 1. Текущий этап и цель

Сейчас проектируется **полная система врагов**, а не только оружие БТР. Дрон-камикадзе и БТР используются как конкретные сценарии для проверки общей архитектуры.

Сначала определяются сущность врага, жизненный цикл, контракты систем, владение состоянием и направление зависимостей. После согласования этой основы составляется план реализации общего фундамента и конкретных видов.

Основные принципы проекта сохраняются:

- Feature-Oriented OOP.
- Composition over Inheritance.
- Zenject для сборки зависимостей и управления их временем жизни.
- Существующий центральный GameLoop.
- Разделение Domain / Application / Infrastructure / Presentation и контрактов в Abstractions.
- ScriptableObject хранит настройки; изменяемое состояние принадлежит экземпляру.

## 2. Отдельный экземпляр врага

Каждый созданный враг — самостоятельный экземпляр со своим префабом, Zenject-контекстом и набором систем.

Два БТР используют одинаковые классы, но имеют разные объекты состояния: собственную цель, углы турели, счётчик выстрелов, таймеры и здоровье. Общий конфиг не становится хранилищем этих данных.

Конкретный вид выражается составом систем, конфигурацией, поведением и представлением. Общая сущность не должна содержать проверки вида «если БТР — стрелять, если дрон — взрываться».

## 3. Общий фундамент Enemy

Реализовано следующее разделение ответственности для общего фундамента:

| Элемент | Слой | Ответственность |
|---|---|---|
| `Enemy` | Core/Domain | Идентичность экземпляра и общее игровое состояние жизни |
| `EnemyLifecycle` | Core/Application | Координация активации, отключения, смерти и завершения работы систем |
| `EnemyRoot` | Core/Infrastructure | Unity-адаптер экземпляра; передаёт события Unity lifecycle в `EnemyLifecycle` |
| Общие контракты | Core/Abstractions и Abstractions соответствующих систем | Взаимодействие через необходимые операции без привязки к конкретному виду |

`Enemy` — обычный C#-класс, содержащий идентификатор экземпляра и состояние жизни. Здоровье, выбранная цель, режим поведения, маршрут и таймеры оружия принадлежат соответствующим системам.

`EnemyLifecycle` координирует системы; `EnemyRoot` передаёт события Unity и готовность Zenject. Модули регистрируют свои обновления в существующем GameLoop при `Activate` и снимают при `Deactivate`. Группы `Gameplay` и `Presentation` задаются через `EnemyModuleGroup`: смерть останавливает игровую логику, сохраняя возможность работы представления до отключения или удаления экземпляра.

Перевод дрона завершён: `KamikazeDroneRoot` и `IDroneRuntimeModule` заменены общими `EnemyRoot` и `IEnemyRuntimeModule`. Движение, обнаружение, атака и представление подключены к общему lifecycle; ссылки префаба обновлены. `EnemyCoreInstaller` собирает зависимости экземпляра и получает модули и роли смерти только из локального контейнера. Установщик движения называется `DroneMovementInstaller`; GUID сохранён.

### Различие смерти, отключения и удаления

- **Отключение:** экземпляр временно не участвует в игре; само по себе не означает смерть.
- **Смерть:** однократный игровой переход, после которого враг больше не принимает решения и не атакует.
- **Удаление:** окончательное освобождение экземпляра и его зависимостей.

Смерть не обязана немедленно удалять модель. Представление может продолжать воспроизводить эффекты или отображать остов. Повторный сигнал смерти не должен повторно запускать её последствия. При повторном включении погибший враг не должен возобновлять боевые действия.

## 4. Интерфейсы и полиморфизм

Согласовано использовать **общие контракты, конкретные реализации систем и композицию экземпляра**.

Состояние контрактов:

| Контракт | Назначение | Статус |
|---|---|---|
| `IEnemy` | Идентификатор `Id` и состояние жизни `IsAlive` | Реализован |
| `IEnemyBehaviour` | Подключение принятия решений конкретного вида через общий контракт | Требует проектирования |
| `IEnemyAttack` | Запуск и прерывание атаки, получение её состояния | Требует проектирования |
| `IEnemyMovement` | Передача команд движения и получение результата | Требует проектирования |
| `IEnemyRuntimeModule` | `Activate(GameLoopRegistry)` и `Deactivate(GameLoopRegistry)` | Реализован |
| `IEnemyDeathSource` | Запрос смерти через событие `DeathRequested` | Реализован |
| `IEnemyDeathListener` | Однократное уведомление `OnOwnerDied()` | Реализован |

Для ещё не реализованных контрактов указаны проектные обязанности, а не готовые сигнатуры. Их общие операции предстоит проверить на сценариях дрона и БТР. В частности, контракт движения должен выражать осмысленные команды и для полёта, и для наземного перемещения.

Иллюстрация предполагаемого полиморфизма; названия не означают наличие таких классов в проекте:

```text
IEnemy                 → Enemy
IEnemyBehaviour        → DroneBehaviour / ApcBehaviour
IEnemyAttack           → DroneAttack / ApcAttack
IEnemyMovement         → реализация полёта / реализация движения БТР
```

Контракт подключения модуля и контракт игровой способности разделяются. Управление lifecycle не должно требовать от каждого модуля методов движения, наведения и стрельбы.

### Абстрактные классы

Абстрактные классы разрешены, но не обязательны для полиморфизма. Наличие интерфейса само по себе не требует общего базового класса.

Базовый абстрактный класс вводится, когда обнаружен общий алгоритм с различающимися шагами. Иерархия `Enemy → VehicleEnemy → ArmoredEnemy → Apc` не принимается за основу системы заранее.

В текущем предложении общие данные и правила жизни реализует `Enemy`, а различающееся поведение находится в подключённых системах. Наследники самой сущности нужны только при появлении собственных обязанностей на этом уровне; выбор набора модулей уже выполняет сборка через Zenject.

## 5. Верхний слой — конкретные виды врагов

Конкретный вид задаёт:

1. **Сборку:** какие системы входят в экземпляр и как соединены.
2. **Поведение:** какие решения принимает этот вид и как координирует способности.
3. **Конфигурацию и представление:** параметры, модель, звук и эффекты.

Общий `EnemyRoot` используется в префабах разных видов. Отдельный `ApcRoot`, повторяющий его обязанности, не требуется.

Примеры состава:

```text
Дрон:
  общий фундамент + обнаружение + выбор цели
  + поведение камикадзе + полёт + подрыв + представление

БТР:
  общий фундамент + обнаружение + выбор цели
  + поведение БТР + движение + турель + оружие + представление
```

Сборка конкретного вида знает о нужных общих системах. Общие сущность, lifecycle и механизмы способностей не должны зависеть от конкретного поведения БТР или дрона.

## 6. Предлагаемая карта систем

```text
Gameplay/Features/
├── Tank/
│   └── Weapon/                         существующее оружие танка
├── Combat/
│   └── Targeting/                      существующие общие боевые цели
└── Enemies/
    ├── Core/                           сущность и общий lifecycle
    ├── Perception/                     общая часть обнаружения врагами
    ├── Targeting/                      общая часть выбора цели врагами
    ├── Combat/
    │   ├── Weapons/                    оружейные механики врагов
    │   └── Projectiles/                снаряды оружия врагов
    ├── KamikazeDrone/                  состав и специфика дрона
    └── ArmoredPersonnelCarrier/        состав и специфика БТР
```

Это предварительная карта ответственности. Папки и слои создаются при появлении соответствующего кода. Общие части обнаружения и выбора выделяются после сравнения реализаций; правила конкретного вида остаются рядом с этим видом.

`Enemies/Combat` предназначен для боевых механик врагов. Танковое оружие остаётся в `Tank/Weapon`; его перенос в универсальную систему боя не согласован.

Существующий `Combat/Targeting` сохраняет `ICombatTarget`, `CombatTarget` и реестр возможных целей. Он предоставляет сведения об участниках, а системы врага определяют, кого обнаружить и выбрать. Общая категория Enemy не заменяет контракт боевой цели.

### Пример разделения атаки БТР

- `ApcBehaviour` принимает решения поведения через необходимые контракты.
- `ApcAttack` организует специфическую атаку БТР.
- `ApcTurretAim` отвечает за наведение турели.
- `BurstWeapon` исполняет работу оружия с очередями.
- `BurstFireCycle` хранит правила и состояние очереди.
- Реализация запуска снаряда выполняет отдельный выстрел.
- Представление реагирует на состоявшиеся выстрелы.

Названия с `Controller` для организации атаки БТР отклонены пользователем. Рабочее название — `ApcAttack`. `APC` означает Armored Personnel Carrier, БТР.

## 7. Владение состоянием и интеграция

| Состояние | Владелец |
|---|---|
| Идентичность и состояние жизни | `Enemy` конкретного экземпляра |
| Здоровье | Система здоровья экземпляра |
| Обнаруженные цели | Система обнаружения экземпляра |
| Выбранная цель | Система выбора цели экземпляра |
| Режим поведения | Поведение экземпляра |
| Маршрут и состояние движения | Система движения экземпляра |
| Наведение | Система турели экземпляра |
| Очередь и пауза | Оружие экземпляра |
| Статические параметры | Соответствующие конфиги |

При интеграции нужно определить единый источник идентичности владельца и связь с его `CombatTarget`. Доступность боевой цели должна учитывать жизнь и участие экземпляра в игре. Сейчас `CombatTarget.IsAvailable` проверяет активность компонента; расширение этой проверки ещё не реализовано.

Unity-события, физические контакты и игровые команды не должны создавать независимые конкурирующие пути смерти или удаления.
