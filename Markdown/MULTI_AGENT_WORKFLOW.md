# Учебный процесс проектирования и делегирования

Дата фиксации: 2026-10-25.

## 1. Цель

Освоить процесс работы Senior Game Developer / системного архитектора на реальных задачах Murky Aces: постановку требований, исследование проекта, выбор архитектуры, декомпозицию, интеграцию и проверку результата.

Пользователю важно видеть полноценное предлагаемое решение и понимать основания решений, чтобы постепенно принимать их самостоятельно. Экономия ресурсов важна, но на первых примерах допускаются более подробные учебные объяснения.

Этот документ задаёт рабочий регламент. Конкретная механика, её задачи и разрешённые изменения описываются в отдельном плане. Запуск исполнителей выполняется по явной команде пользователя. Подготовленный код сначала показывается пользователю; изменения в проект вносятся после его одобрения конкретного блока кода.

## 2. Текущий режим: сначала план и обсуждение

Выбран вариант 1:

1. Основной агент в роли Senior / архитектора изучает задачу и существующий проект.
2. Показывает целостное предлагаемое решение и объясняет существенные решения.
3. Обсуждает с пользователем варианты и корректирует план.
4. По запросу оформляет согласованный план механики в `PLAN_DELEGATION.md`.
5. По явной команде пользователя начинает подготовку кода очередной задачи, при необходимости с субагентом. Файлы проекта на этом этапе не изменяются.
6. Показывает подготовленный код, обсуждает замечания и ждёт одобрения перед применением изменений.
7. Применяет одобренный блок, выполняет проверки и передаёт результат на игровую приёмку.

На этапе планирования работа ограничивается чтением и анализом. Создание или обновление документации выполняется в согласованном объёме. Сборки, тестовые запуски и изменения сцен, префабов, конфигов, зависимостей или исходников не запускаются автоматически.

Пользователь управляет переходами от обсуждения к подготовке кода, одобряет код перед применением и принимает игровой результат. Координацию разрешённых задач основной агент выполняет внутри текущего чата. Этот порядок действует и для небольших правок.

## 3. Контекст проекта

- Unity 6, C#.
- Feature-Oriented OOP, Composition over Inheritance.
- Zenject DI и явный центральный GameLoop.
- Слои Domain / Application / Infrastructure / Presentation и контракты в Abstractions там, где они нужны.
- Существующие решения и ограничения проекта описаны в [CODEX_Murky_Aces.md](CODEX_Murky_Aces.md) и README соответствующих систем.

Перед проектированием Senior проверяет актуальное состояние нужных файлов. Ранее выполненный обзор не заменяет проверку конкретных точек интеграции. Существующие механизмы используются повторно, если подходят задаче; новые слои и абстракции вводятся с конкретным обоснованием.

## 4. Учебный формат

Основной формат объяснения:

> Что нашли в проекте → какие есть варианты → что выбираем и почему → как проверим результат.

Сначала пользователь получает целостную картину решения: от игрового действия до изменения состояния и отображения результата. Затем обсуждаются отдельные архитектурные развилки.

Для каждой существенной развилки допустимы оба способа:

- Senior сначала показывает предложение и объясняет его последствия.
- Пользователь сначала предлагает свой вариант, после чего варианты сравниваются вместе.

Не нужно требовать от пользователя самостоятельно спроектировать всю систему, прежде чем показать рабочее предложение. Не нужно и лишать пользователя возможности предложить своё решение.

В объяснениях показываются факты, допущения, альтернативы, аргументы и практические последствия. Обсуждается как необходимость новых классов и интерфейсов, так и возможность обойтись существующим кодом.

### Просмотр кода перед применением

- Код показывается законченными небольшими задачами: например, состояние механики и работающая с ним логика вместе.
- Для новых классов показывается полный код. Для существующих файлов показываются точные изменения с достаточным контекстом, например unified diff.
- Основной агент объясняет назначение изменений, связи с существующим кодом и существенные решения. Если код готовил субагент, основной агент сначала проверяет его сам.
- Пользователь читает код, задаёт вопросы и предлагает исправления. После обсуждения ему показывается окончательный вариант блока.
- До одобрения код предоставляется в ответе чата. Исходники, сцены, префабы и конфиги проекта остаются без изменений; черновые скрипты в Assets не создаются.
- Одобрение относится к конкретному показанному блоку. Изменённый по существу вариант и последующие исправления кода проходят такой же просмотр перед записью.
- Согласованные обновления документации выполняются по запросу пользователя; просмотр игрового кода не препятствует ведению MD-плана.

## 5. Последовательность работы над механикой

### Шаг 1. Сформулировать результат

- Описать основные игровые сценарии и ожидаемое поведение.
- Определить границы задачи: что входит сейчас и что отложено.
- Зафиксировать критерии готовности.
- Выделить вопросы, ответы на которые действительно меняют решение.

### Шаг 2. Исследовать существующий код

- Найти подходящие системы, состояния, контракты, installers и точки GameLoop.
- Проверить создание, владение состоянием, отключение и удаление затрагиваемых объектов.
- Учитывать текущие изменения пользователя и принятые архитектурные решения.
- Отделить подтверждённые факты от предположений.

### Шаг 3. Предложить целостную архитектуру

- Показать поток данных и вызовов для основных сценариев.
- Назначить ответственность классам и определить владельцев состояния.
- Описать необходимые контракты и направление зависимостей.
- Указать точки интеграции с существующими системами.
- Рассмотреть значимые отказы, отмену операций и lifecycle.
- Обосновать решения по производительности там, где задача этого требует.

### Шаг 4. Обсудить решения

- Сравнить существенные варианты по сложности, зависимостям, проверяемости и расширению.
- Дать пользователю возможность предложить альтернативу.
- Явно отметить неизвестные моменты и способы их проверки.
- Обновить предложение по результатам обсуждения.

### Шаг 5. Декомпозировать работу

- Задать контракты и состав данных до независимой реализации зависимых частей.
- Каждой задаче назначить исполнителя, результат, набор файлов и критерии приёмки.
- Указать зависимости и порядок выполнения; выделить действительно независимые задачи.
- Исключить одновременное редактирование общих файлов разными агентами.
- Назначить ответственного за общую интеграцию и проверку.
- Для каждой делегируемой задачи объяснить, какую самостоятельную работу выполнит субагент и что в это время делает основной агент.

### Шаг 6. Согласовать план

Пользователь видит полный путь до готовой механики, задачи исполнителей и способы проверки предположений. Вопросы, меняющие поведение, контракты или границы изменений, решаются до запуска соответствующей задачи. После согласования плана Senior ждёт явной команды на подготовку кода и делегирование. Применение кода остаётся отдельным этапом после просмотра.

### Шаг 7. Подготовить код без изменения проекта

Исполнитель готовит код согласованной задачи и необходимые интеграционные изменения в виде предложения. При делегировании основной агент явно запрещает запись в файлы проекта до одобрения. Основной агент проверяет предложение на соответствие архитектуре, затем показывает его пользователю и объясняет решения.

### Шаг 8. Обсудить код и получить одобрение

Пользователь просматривает законченный блок кода. Замечания разбираются, предложение корректируется. Перед записью основной агент получает явное одобрение окончательного варианта, например: «Код T01 одобряю, вноси».

### Шаг 9. Применить, проверить и принять

После одобрения один исполнитель вносит показанные изменения и выполняет интеграцию в разрешённых файлах. Основной агент проверяет соответствие внесённого результата одобренному коду и выполняет предусмотренные технические проверки. Пользователь выполняет игровую приёмку по подготовленному сценарию. Исправления, выявленные проверками, сначала показываются пользователю. Изменения согласованного поведения, контрактов или границ возвращаются на архитектурное обсуждение.

Шаги 7–9 повторяются для очередных задач MD-плана.

Статусы фиксируются по результату:

- **Спроектировано:** согласованы архитектура, задачи и критерии готовности.
- **Код подготовлен:** предложение проверено основным агентом и показано пользователю; файлы проекта не изменены.
- **Код одобрен:** пользователь разрешил применить конкретный показанный блок.
- **Реализовано:** внесены предусмотренные изменения и выполнена интеграция.
- **Проверено:** пройдены предусмотренные технические проверки и ревью; фактические результаты перечислены в отчёте.
- **Принято:** пользователь подтвердил игровой результат.

## 6. Модель и роли

Для основного агента и всех субагентов используется **GPT-6.1 Sol (`gpt-6.1-sol`)**. Astra и Terra в текущую схему не входят. Уровень рассуждения наследуется из настроек основного чата; отдельные изменения модели или уровня выполняются по указанию пользователя.

Пользователь выбирает GPT-6.1 Sol для основного чата. При запуске субагентов используется та же модель; настройки в этом документе служат регламентом и не переключают модель уже открытого чата.

| Роль | Модель | Ответственность |
|---|---|---|
| Архитектор / координатор | GPT-6.1 Sol | Основной агент: требования, обучение, архитектура, контракты, задания, координация, ревью и ответственность за итоговую интеграцию |
| Исполнитель | GPT-6.1 Sol | Подготовка согласованной логики, математики, физики, данных, конфигов и интеграционных изменений; применение показанного кода после одобрения пользователя |
| Ревьюер | GPT-6.1 Sol | Независимая проверка предложенного кода или внесённых изменений, связанных сценариев и соблюдения контрактов; по умолчанию без редактирования файлов |

Роль обозначает ответственность. Ко всем исполнителям предъявляются одинаковые требования к качеству. Названия Middle / Junior для ограничения инженерных возможностей не используются. Роль исполнителя можно уточнить: «исполнитель логики» или «исполнитель изолированных задач».

Основной агент может самостоятельно выполнять реализацию небольшой задачи. Отдельный агент подключается под конкретный результат. Три роли не требуют трёх одновременно работающих агентов: исполнитель и ревьюер могут запускаться последовательно.

## 7. Запуск, параллельность и рабочая папка

- Основной агент работает в текущем чате и сам создаёт субагента после разрешения пользователя на делегирование. Ручное создание отдельных чатов и перенос сообщений пользователем не требуются.
- По умолчанию работают **один основной агент и максимум один активный субагент**. Расширение состава требует явного указания пользователя.
- Субагент получает задание и необходимый контекст от основного агента. Создание им дополнительных агентов не входит в разрешённую задачу.
- Используется текущая общая рабочая копия проекта. В рамках этого регламента отдельные worktree не создаются автоматически.
- На первых учебных проходах **код и Unity-ассеты меняет один исполнитель за раз**. Основной агент не редактирует проект одновременно с исполнителем.
- Подготовка кода субагентом выполняется без записи в файлы проекта. После просмотра и одобрения основной агент применяет код сам либо передаёт исполнителю разрешение на запись конкретного одобренного блока.
- Параллельность применяется прежде всего для независимого исследования и проверок. Основной агент и субагент получают разные вопросы или области анализа.
- Контракты согласуются до реализации. Зависимые шаги выполняются последовательно: контракт → подготовка кода → просмотр и одобрение → применение и интеграция → проверка.

| Ситуация | Порядок работы |
|---|---|
| Обсуждение требований и архитектуры | Основной агент вместе с пользователем |
| Небольшая правка | Основной агент готовит и показывает код, после одобрения применяет и проверяет |
| Исследование двух независимых подсистем | Основной агент изучает одну, субагент — другую |
| Реализация согласованной механики | Один исполнитель готовит очередной блок; координатор проверяет и показывает его пользователю до применения |
| Ревью сложного изменения | До применения проверяется предложение; после применения и интеграции — фактический diff и связанные сценарии |

До делегирования основной агент проверяет три условия:

1. У задачи есть самостоятельный результат и критерии приёмки.
2. Работа достаточно независима и не требует постоянного ожидания решений другого агента.
3. Для передачи достаточно компактного задания и связанных файлов.

Если условия не выполняются, задача остаётся у основного агента или делится иначе. Во время работы исполнителя координатор занимается отдельной необходимой работой либо ждёт результат; повторная реализация той же задачи не выполняется.

## 8. Границы изменений

Для каждой механики составляются три явных списка:

1. **Forbidden paths:** файлы и области, которые нельзя менять в рамках задачи.
2. **Разрешённые точки интеграции:** существующие файлы, которые можно расширить, с описанием допустимых изменений.
3. **Новые файлы:** ожидаемые пути и ответственный исполнитель.

Разрешённые пути задают границы задачи. Запись в них начинается после одобрения показанного кода. Если требуются изменения Unity-ассетов, их состав и ожидаемое поведение также показываются до применения.

Запреты определяются по конкретной задаче. Не следует объявлять весь core навсегда неизменяемым: необходимое изменение существующей системы должно быть выявлено и согласовано в плане.

Если задача требует выхода за разрешённые границы, исполнитель сообщает причину и предлагает решение основному агенту. Основной агент возвращает пользователю изменения согласованного поведения, контрактов, Forbidden paths или объёма задачи. Локальные решения внутри утверждённых границ исполнитель принимает самостоятельно.

## 9. План, задания и отчёты

План конкретной механики оформляется в `Markdown/PLAN_DELEGATION.md` и содержит:

1. Цель, игровые сценарии и критерии готовности.
2. Границы задачи и отложенные возможности.
3. Найденные существующие механизмы и точки интеграции.
4. Архитектуру: ответственность, состояние, контракты, поток данных и lifecycle.
5. Выбранные решения, существенные альтернативы и способы проверки предположений.
6. Forbidden paths, разрешённые изменения и новые файлы.
7. Задания необходимых исполнителей с указанием роли и модели GPT-6.1 Sol.
8. Зависимости задач, порядок выполнения и ответственного за общие файлы.
9. План интеграции и проверки, включая значимые негативные сценарии.
10. Текущий статус согласования и разрешения на реализацию.

Для каждой задачи план отдельно фиксирует подготовку предложения, просмотр кода пользователем, одобрение, применение и результат проверок. Одобрение архитектуры не заменяет просмотр кода.

Для каждой задачи нужны: конкретный результат, входные контракты, разрешённые файлы, ограничения, зависимости и способ приёмки. В плане можно описывать сигнатуры и состав данных, но реализация кода на этапе планирования не выполняется.

### Шаблон задания исполнителю

1. **ID и роль:** например, T01, исполнитель логики.
2. **Цель и результат:** что должно быть получено.
3. **Контекст:** какие файлы и решения нужно прочитать.
4. **Контракты:** входы, выходы, состояния и связи с другими системами.
5. **Разрешённые изменения:** существующие и новые файлы.
6. **Ограничения:** Forbidden paths и запрещённые изменения поведения.
7. **Зависимости:** что должно быть готово до начала.
8. **Режим работы:** подготовить предложение без записи либо применить конкретный блок, уже одобренный пользователем. Для применения указывается одобренный вариант.
9. **Проверки и приёмка:** проверка предложения до применения, компиляция и необходимые игровые проверки после применения.
10. **Отчёт:** короткий результат по шаблону ниже.

### Шаблон отчёта исполнителя

1. **Выполнено:** подготовленное предложение и целевые файлы либо применённые изменения и фактически изменённые файлы; эти результаты различаются явно.
2. **Проверено:** выполненные проверки и их фактические результаты; невыполненные проверки указываются отдельно.
3. **Отклонения и препятствия:** что отличается от задания и почему.
4. **Вопросы координатору:** решения, необходимые для продолжения или приёмки.

## 10. Разрешение на запуск и приёмка

Примеры команд пользователя:

- **«Подготовь план механики …, без реализации»** — исследование и обсуждение основным агентом, подготовка документа; исполнители не запускаются.
- **«Создай субагента для анализа …, только чтение»** — разрешение на конкретную исследовательскую задачу без изменений проекта.
- **«План принят, запусти T01 через субагента»** — утверждение плана и разрешение подготовить код T01 с делегированием, без записи в проект.
- **«План принят, выполняй задачи по порядку с субагентами»** — разрешение готовить задачи по плану с соблюдением лимита одного активного субагента и остановкой на просмотре кода перед каждым применением.
- **«Код T01 одобряю, вноси»** — разрешение применить показанный окончательный блок T01 и выполнить предусмотренные проверки.

Утверждение плана и разрешение запуска подготовки могут быть даны одной командой. Разрешение на подготовку и делегирование сохраняется на весь указанный объём. Применение каждого законченного блока требует одобрения показанного кода. Уже одобренный блок применяется целиком: повторное подтверждение каждого входящего в него файла не требуется. Обычные вопросы и обсуждение плана не запускают реализацию.

До применения основной агент проверяет предложенный код по чтению и объясняет его пользователю. После применения выполняются компиляция и необходимые проверки поведения. Результат просмотра предложения не обозначается как успешный прогон компиляции или тестов.

Разрешение на применение блока включает технические проверки, указанные в его плане, в пределах доступных разрешений среды. Проверки выбираются по риску изменения; повторяются после новых изменений, сбоев или при нерешённых проблемах. Для простых обратимых изменений не создаются тесты, повторяющие реализацию. Если для исправления результата проверки нужно изменить код, исправление сначала показывается пользователю и применяется после одобрения.

После технической проверки основной агент показывает результат, объясняет существенные решения и предоставляет сценарий игровой приёмки. Пользователь подтверждает результат или возвращает конкретные замечания. Исправления выполняются в рамках разрешённого объёма.

## 11. Контроль расхода ресурсов

- Для каждого дополнительного агента указывается конкретная польза запуска.
- Исполнителю передаются его задача, связанные файлы, контракты и ограничения; полный повторный обзор проекта для небольшой задачи не выполняется.
- Координатор не дублирует исследование и реализацию исполнителя. При ревью он проверяет результат и связанные риски.
- Отчёты короткие; подробные учебные объяснения сосредоточены на существенных решениях в основном чате.
- Код рассматривается законченными небольшими задачами. Новый класс показывается полностью, изменения существующего файла — с достаточным контекстом; просмотр каждой отдельной строки не превращается в самостоятельный этап.
- Уже пройденные проверки повторяются при новых изменениях, сбоях или нерешённых проблемах.
- Маленькие задачи остаются у основного агента. Передача работы должна оправдывать подготовку задания и интеграцию результата.
- После первых **3–5 задач** оцениваются время выполнения, доступные данные о расходе ресурсов, количество уточнений и переделок, время интеграции и понятность процесса для пользователя. Отсутствующие измерения отмечаются явно.
- Если передача и интеграция обходятся дороже полученной пользы, уменьшается число делегируемых задач.
- По мере освоения процесса повторяющиеся объяснения сокращаются; сохраняются основания новых решений и критерии проверки.

Рабочая последовательность: **исследование → целостное предложение → совместное обсуждение → MD-план → разрешённая подготовка кода → просмотр и обсуждение кода → одобрение → применение и интеграция → проверки → игровая приёмка**.
