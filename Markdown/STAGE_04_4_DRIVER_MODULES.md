### Согласованные решения

- Выход из кресла уже выполняется повторной интеракцией с люком. Отдельную кнопку F для выхода добавлять не требуется.
- Фары управляются обычным Press через кнопку. Анимацию физического тумблера пользователь пока не делает.
- Фары при старте выключены; выход водителя сохраняет выбор; disable танка гасит свет, enable восстанавливает выбранное состояние. Управлять может только игрок в кресле водителя.
- Ссылка на TankRoot в LightsSwitchInteractable пользователем убрана; не возвращать её автоматически.
- Для топлива сейчас согласован полный бак, в дальнейшем старт будет с пустым баком и поиском топлива. В сохранённом TankFuelConfig сейчас ёмкость 100 и Initial Fill = 0.5 после проверки. Для согласованного старта вернуть 1; будущий старт с пустым баком — 0.
- Initial Fill читается при создании TankFuelState. Изменение конфига во время Play Mode не меняет уже созданный бак; для проверки начального значения перезапускать Play Mode.
- ПНВ при старте выключен; доступ только водителю в кресле; выход сохраняет выбранный режим. Фактический эффект работает при активном внешнем видеоканале.
- Приоритет ПНВ — различимость дороги, склонов и препятствий ночью. Шум и виньетка не являются обязательными для первого полезного варианта.
- Текущая работа — GPS; затем радиостанция и общая финальная проверка. Незакрытые проверки радара сохраняются. Номера разделов сохранены из исходного плана.
- Радар отображает только врагов и технику. Дружественных игроков сейчас не показывать.
- Категории радара расширяются через `IRadarTarget`, `RadarTargetDefinition` и список разрешённых типов в `TankRadarConfig`; добавление категории не требует условий по типам в scanner или Presenter.
- Радар обнаруживает цели через препятствия; проверки прямой видимости и физических лучей в scanner нет.
- Текущий конфиг радара: Range = 100, Scan Interval = 0.5, Initially Enabled = false; разрешены категории enemy и vehicle.
- При выключении радара контакты очищаются. Выбор вкл/выкл принадлежит танку; код не сбрасывает его при выходе водителя или временном disable танка. Фактическое восстановление после disable/enable ещё проверить.
- Управление радаром разрешено только игроку в кресле водителя и только при зарегистрированном scanner.
- Верх экрана радара соответствует направлению корпуса на горизонтальной плоскости, не направлению башни; цвета берутся из конфигов категорий. Экран показывает до 64 ближайших контактов, scanner этим лимитом не ограничен.
- GPS: водитель и командир входят во взаимодействие через E; камера приближается к экрану, затем становится доступен ввод GPS. Повторное E возвращает камеру и управление; кресло остаётся занятым.
- Оба игрока меняют масштаб своей карты независимо. Командир выбирает одно назначение кликом; начальная точка определяется автоматически по позиции танка. Последовательное рисование маршрута кликами заменено этим UX.
- Первый расчёт маршрута выполняется только по дороге. Сейчас карта содержит одну открытую ломаную без развилок; поиск оптимального пути по сети дорог относится к будущему расширению.
- Жёлтая линия показывает всю дорогу, розовая — рассчитанный маршрут, оранжевая точка — назначение, спроецированное на дорогу. Начало пути пока фиксируется в момент выбора назначения.
- Маршрут принадлежит танку; камера, ввод и временная GPS-сессия принадлежат игроку; масштаб и графические ресурсы принадлежат отдельному экрану.
- Проверку GPS при спавне танка пользователь отложил до реализации спавна. Плавающая ошибка восстановления input при закрытии GPS также отложена: сейчас стабильно не воспроизводится.

### Фактическое состояние радара

- `TankRadar` хранит выбранный режим и снимок `RadarContact`; ID целей имеют тип `ulong`.
- `RadarTarget` реализует `IRadarTarget`, получает общий `RadarTargetRegistry` через DI и регистрируется по Unity lifecycle. ID формируется через `EntityId.ToULong(GetEntityId())`, без устаревшего `GetInstanceID()`.
- `RadarTargetRegistryInstaller` устанавливает реестр на уровне сцены; `TankRadarInstaller` создаёт состояние и зависимости конкретного танка.
- `TankRadarScanner` работает в gameplay-фазе через `ITankRuntimeModule`, фильтрует доступность, разрешённые категории, собственную цель и сферическую дальность. Выключенный радар не сканирует; unregister очищает контакты без сброса выбранного режима.
- `TankRadarCommands` проверяет occupancy водителя; `RadarSwitchInteractable`, proxy collider, `InteractionTargetLink` и scope подключены. Пользователь подтвердил работу кнопки и `Contacts.Count = 0` при выключении.
- `TankRadarPresenter` зарегистрирован в presentation-фазе, переводит позиции контактов в координаты относительно корпуса и передаёт цвета категорий в `TankRadarDisplayView`.
- `TankRadarDisplayView` передаёт состояние и массивы контактов через `MaterialPropertyBlock` в `TankRadarDisplay.shader` на существующем `Driver_Radar_Screen`, material slot 0. Отдельные Canvas, камера или RenderTexture для радара не нужны.
- Ошибка отсутствующего `_ContactCount` устранена дополнением shader; после подключения Presenter пользователь подтвердил: «всё появилось».
- В текущем `TankRadarCommands.TrySetEnabled` ещё присутствует временный `Debug.Log`. В `TankRadarInstaller.InstallBindings` проверка View есть, но прежняя проверка `_config == null || !_config.IsValid` отсутствует перед чтением `InitiallyEnabled`. Эти правки пользователь делает отдельно после проверки; при обновлении документа реализация не изменяется.

- `GpsRouteState` реализует `IGpsRouteReader`, хранит точки, назначение и ревизию. `GpsRouteService` проверяет занятость кресла командира и строит путь от текущей позиции танка; при неудаче сохраняет предыдущий маршрут.
- `GpsPolylineRoutePlanner` проецирует начало и назначение на ближайшие сегменты дороги и возвращает участок ломаной в нужном направлении. Развилки и граф дорог сейчас не поддерживаются.

- `TankGpsInstaller` создаёт одно состояние и сервис маршрута на танк. Для каждого установленного экрана создаётся отдельный `GpsPresenter`, читающий общий маршрут и положение корпуса; Presenter работает в presentation-фазе через `ITankRuntimeModule`.

## 1. Формат совместной работы

Сохраняется формат, зафиксированный в плане командира:

> Код не менять — я сам буду вносить изменения, ты просто показывай код.
> Перед кодом — логическое объяснение, почему именно так ты хочешь сделать.

- Ассистент объясняет один небольшой шаг, затем показывает код и точные места добавления или замены.
- Исходный код, префабы, сцены, конфиги и настройки реализации пользователь меняет самостоятельно.
- После кода указывать действия в Inspector и способ проверки результата.
- Показанный код не означает выполненный этап. Отмечать реализацию после подтверждения пользователя или проверки внесённых изменений.
- Обновление этого документа не является разрешением менять реализацию.

### 1.1. Обязательная архитектурная проверка перед каждым шагом

Перед каждым новым шагом ассистент обязан проверить связанные классы и зависимости целиком, а не только место добавления очередного метода. Небольшие шаги должны сохранять границы ответственности системы.

До предложения кода необходимо:

1. Определить, кому принадлежит новая ответственность и к какому слою она относится: Domain, Application, Presentation или Infrastructure.
2. Проверить, не смешиваются ли в одном классе runtime-состояние, игровые команды, ввод, преобразование данных и отображение; нет ли дублирования существующей логики.
3. Проверить владельца состояния и его lifetime: общий танк, конкретный игрок, временная сессия или отдельный экран.
4. Оценить, нужен ли рефакторинг до добавления функциональности. При нарушении границ ответственности сначала явно объяснить проблему и предложить конкретное разделение классов, затем показать необходимый рефакторинг в согласованном формате работы.

При обнаружении архитектурной проблемы добавление зависимой функциональности откладывается до необходимого разделения. Ассистент должен выявлять такие проблемы самостоятельно, не дожидаясь замечания пользователя. Название `Test`, `Sandbox` или статус прототипа не отменяют эту проверку.

Рефакторинг выполнять небольшими проверяемыми шагами: сохранять работающее поведение, DI-сборку, Inspector-ссылки, регистрацию в GameLoop и существующий путь ввода. Новые классы и абстракции вводить под конкретные ответственности; одного переименования перегруженного класса недостаточно.

Для текущего GPS перед каждым продолжением проверять структуру всей feature, включая `GpsMapView` и его помощников, Presenter, GPS-сессию, ввод и сервис маршрута. Прежний перегруженный `TestMapView` уже разделён; новые обязанности не собирать обратно в View. Исходный код и настройки по-прежнему меняет пользователь самостоятельно.

## 2. Результат задачи

Водитель использует приборы и физические органы управления своей панели через существующую Interaction feature, сохраняя возможность вести танк и осматриваться.

| Элемент | Назначение | Взаимодействие |
|---|---|---|
| Датчик топлива | Показ количества топлива танка | Чтение показаний |
| Экран внешней камеры корпуса | Изображение существующей внешней камеры | Существующее поведение |
| Тумблер фар | Управление фарами танка | Press: вкл/выкл |
| Дополнительная радиостанция | Управление установленной радиостанцией | Press: вкл/выкл |
| Дополнительный радар | Управление установленным радаром и отображение результатов | Press: вкл/выкл |
| Дополнительный экран GPS | Отображение общего маршрута танка | E: приближение камеры/выход; локальный зум; выбор назначения доступен командиру |
| Дополнительный тумблер ПНВ | Управление режимом внешней камеры | Press: вкл/выкл |

Дополнительные устройства доступны только в комплектации, где они присутствуют. Поддержка установки и снятия во время миссии в этот этап не входит.

|---|---|---|
| `TankRoot` | Получает список `ITankRuntimeModule`, регистрирует и снимает их при изменении Unity lifecycle | Подключать обновления новых систем через существующий механизм |
| `ITankRuntimeModule` | Контракт регистрации в `GameLoopRegistry` | Не считать его контрактом физического оборудования или слота |
| `DriverStationAdapter` | Передаёт driving intent в `TankMovement` | Сохранить ответственность за движение |
| `CrewStationController` | Посадка, выход, occupancy, роль; включает и выключает необязательный display feed | При необходимости расширить только подключение представлений станции |
| `StationDisplayFeed` | Камера, собственный runtime RenderTexture, вывод через MaterialPropertyBlock | Сохранить для внешнего видеоканала |
| `StationPanelRoot` | Ссылка на один основной экран и material slot | Дополнительные приборы подключать явными ссылками |
| `StationInteractionScope` | Разрешённые иерархии и конкретные interaction targets | Включить новые органы управления в scope водителя |
| `InteractionTargetLink` | Связывает collider и `IInteractable` | Использовать на proxy colliders тумблеров |
| `GameLoopRegistry` | Input, gameplay, fixed gameplay, presentation | Выбирать фазу по ответственности класса |

Исходный аудит выполнялся до реализации новых устройств. Сейчас в runtime-коде есть системы фар, топлива, ПНВ, радара и GPS; их текущий статус указан в разделе 0 и чек-листах ниже. Текущая работа — завершение GPS, следующий модуль — радиостанция. Незавершённые проверки остальных устройств сохраняются.

Текущие ограничения:

- `CrewStationView.CanEnter` требует валидный основной экран. Отсутствие ссылки может блокировать посадку; отказ `StationDisplayFeed.TryActivate` после посадки обрабатывается иначе и не отменяет её.
- Камера активируется после успешной посадки и деактивируется после успешного выхода.
- Состав `ITankRuntimeModule` получается при сборке танка. Изменение комплектации в runtime потребует отдельного решения.
- Sandbox `ToggleInteractable` переключает активность GameObject. Для реальных устройств источником состояния должен стать runtime-объект устройства.

## 4. Предлагаемая архитектура

Базовый подход: **независимые устройства танка + небольшой состав представлений панели**. Реализовывать по одному устройству; общие abstractions выделять после появления реального повторения.

### 4.1. Владение состоянием

- Состояние оборудования принадлежит танку и создаётся в его DI-контексте.
- Состояние ввода, текущего игрока и временных сессий принадлежит игроку.
- `DriverStationAdapter` не становится владельцем всех водительских приборов.
- `StationPanelRoot` и представления не рассчитывают расход топлива, обнаружение целей или маршрут.
- ScriptableObject хранит статические настройки. Текущее количество топлива, положение тумблеров и маршрут хранятся в отдельных runtime-объектах.

### 4.2. Путь команды

```text
Существующий input pipeline
    → PlayerInteraction
    → предметный IInteractable.Complete(context)
    → команда устройства с проверкой условий
    → runtime-состояние
    → Presenter / Unity View
```

`GetInteractionInfo` сообщает доступность. Выполнение команды повторно проверяет актуальные условия и права игрока. Scope ограничивает поиск цели, но не заменяет предметную проверку доступа при выполнении.

Использовать существующие Press lifecycle, HUD, physics target finder и scope. Отдельную систему ввода для тумблеров не создавать.

### 4.3. Presentation и GameLoop

- Gameplay реализуется обычными C#-классами с явными зависимостями.
- Unity-компоненты работают с Light, Camera, Renderer, аудио и визуальным положением тумблера.
- Gameplay-обновления регистрируются в gameplay-фазе, физически зависимые — в fixed gameplay, представления — в presentation.
- Классу, который только принимает команды и хранит состояние, собственный tick не нужен.
- R3 допустим для отражения состояния в presentation. Он не заменяет явный поток gameplay-команд.
- Не вводить глобальный EventBus, runtime Service Locator, универсальный менеджер устройств или собственные Update для gameplay.

### 4.4. Состав панели и экраны

Сначала использовать явные ссылки на конкретные приборы и представления. Если для нескольких экранов требуется общий lifecycle, выделить небольшой `StationPanelPresentation` или аналогичный объект композиции.

Он отвечает за активацию и завершение работы представлений станции. Он не управляет предметной логикой устройств.

- `StationDisplayFeed` сохраняется для внешней камеры.
- GPS и радар получают независимые представления и собственные ресурсы, если нужны текстуры.
- Не выводить GPS через фиктивную внешнюю камеру и не добавлять его логику в `StationDisplayFeed`.
- Для RenderTexture и изменяемых свойств материала сохранить владение ресурсами конкретным экземпляром.
- Не искать элементы через имена или `Transform.Find`; ссылки назначать явно.
- Исходную геометрию и иерархию модели танка сохранять; органы управления связывать через отдельные логические объекты и proxy colliders.

### 4.5. Дополнительная комплектация

На этом этапе комплектация задаётся префабом и установщиками:

- Установленное устройство получает свои bindings, представления и targets.
- Отсутствующий модуль не должен создавать обязательную зависимость для водительской станции или блокировать сборку танка.
- Не добавлять обязательную constructor-зависимость от всех дополнительных устройств в общий контроллер станции.
- Отсутствующие органы управления скрываются или недоступны по выбранному UX.
- Неиспользуемые интерфейсы, пустые feature-папки, слоты и систему установки заранее не создавать.

### 4.6. Lifecycle

Различать наличие устройства, выбранное состояние вкл/выкл, фактическую работоспособность и активность отображения. Вводить отдельные поля только когда соответствующее различие действительно требуется.

Для фар, ПНВ, радара и GPS выбранное поведение описано в разделе 0; подробная приёмка lifecycle остаётся открытой. Для радио правила уточнять перед зависимой реализацией:

- Выход водителя не сбрасывает выбранное состояние фар, радио и радара.
- Маршрут GPS сохраняется после выхода из кресла.
- Отображение приборов можно приостанавливать отдельно от работы оборудования.
- Выход водителя не удаляет оборудование и его runtime-состояние.
- Disable/destroy танка завершает эффекты, звук, обновления, камеры и освобождает ресурсы.

Очистка регистрации и presentation не должна случайно превращаться в сброс сохранённого маршрута или положения тумблеров при временном disable. Поведение повторного enable определить явно.

## 5. Открытые решения

Обсуждать каждый пункт перед этапом, который от него зависит. Остальные независимые шаги можно продолжать.

| Решение | Что требуется определить | Перед каким этапом |
|---|---|---|
| Начальное состояние и выход из кресла | Фары, ПНВ и радар: выключенный старт, выбранный режим сохраняется; для радара ещё подтвердить lifecycle. Уточнить радио | Следующий модуль и ручная приёмка |
| Доступ к тумблерам | Для фар, ПНВ и радара — только игрок в кресле водителя; радио уточнить отдельно | Подключение interactions |

| Топливо | Ёмкость в конфиге сейчас 100; полный бак сейчас и пустой в дальнейшем согласованы. Уточнить игровые единицы, расход, заправку и поведение при пустом баке | Реальная симуляция топлива |

Доступность устройств при повреждении, ремонт, питание и установка во время миссии — отдельные последующие механики. Этот план не выбирает их правила заранее.

Результат первого среза: пользователь подтвердил взаимодействие и появление контактов. Правила обнаружения и lifecycle реализованы в коде, но подробные сценарии выше не считать проверенными по одному подтверждению отображения. Работа уже продолжена с GPS; это не закрывает оставшуюся приёмку радара.

Текущий результат: командир выбирает назначение, оба экрана читают рассчитанный маршрут. Жёлтая линия — вся дорога, розовая — выбранный путь, оранжевая точка — назначение на дороге. При движении начало розовой линии пока не обновляется.

Прежнее решение отложить приближение камеры заменено решением пользователя: приближение уже реализовано для обеих ролей. От последовательного рисования точек перешли к выбору одного назначения и автоматическому построению по дороге.

Отложено отдельно: проверка GPS при спавне танка и плавающая ошибка `Cannot switch to actions 'Driving'; input is not enabled` при завершении взаимодействия. Вернуться к ним при реализации спавна и при воспроизведении ошибки соответственно. Граф дорог с развилками, поиск оптимального пути по нему и поведение прибытия уточнять перед соответствующим расширением; не считать их уже реализованными.

## 7. Предлагаемое размещение

Названия уточнять при реализации. Папки и классы создавать только по мере необходимости.

```text
Tank/
├── Fuel/               # данные топлива, изменение количества, датчик
├── Modules/
│   ├── Lights/         # команды, состояние, тумблер и свет
│   ├── Radio/          # устройство, тумблер и аудио
│   ├── Radar/          # сканирование, результаты, тумблер и экран
│   ├── GPS/            # общий маршрут и независимые представления
│   └── NightVision/    # режим внешней камеры, тумблер и эффект
└── Stations/           # посадка, роли, scope и композиция панели
```

Внутри каждой feature использовать Domain/Application/Presentation/Infrastructure только в необходимом объёме. Не добавлять формальные слои без ответственности.

## 8. Проверки и критерии готовности

Автоматизировать значимые предметные правила по мере их появления: пределы топлива, доступ к командам, работа выключенного радара, сохранение общего маршрута. Не создавать тесты, которые только повторяют простое переключение поля или Unity View.

Ручная приёмка:

- [ ] Одно нажатие выполняет одно действие; смена Action Map не активирует тумблер повторно.
- [ ] Недоступное устройство не выполняет команду.
- [ ] Разрешённые targets доступны из кресла; scope не открывает случайные внешние взаимодействия.
- [ ] Состояние, индикация и эффект согласованы.
- [ ] Отсутствие дополнительного устройства не мешает посадке и движению.
- [ ] Выход и повторная посадка соответствуют согласованным правилам сохранения состояния.
- [ ] Disable/enable не создаёт повторных регистраций или потерянных ресурсов.
- [ ] Destroy завершает обновления и освобождает ресурсы устройств.
- [ ] GPS водителя и командира читают общий маршрут.
- [ ] ПНВ изменяет только нужный видеоканал.
- [ ] Изменения не нарушили движение, cockpit look, внешнюю камеру и выход.

Сетевой слой подключается после определения его архитектуры. Общее состояние танка и команды доступа проектируются явно, но локальная приёмка не подтверждает сетевую работоспособность.

## 9. Как продолжать работу

1. Начать с раздела 0: текущая задача — завершение GPS (04.4.7). Не создавать повторно готовые классы и не возвращать всю логику в View.
2. Подготовить повторный расчёт в `GpsRouteService`, затем подключить обновление оставшегося пути через отдельный gameplay-модуль. Предложенный код ещё не считается внесённым.
3. Подключить очистку маршрута, поддержать отсутствие водительского GPS и выполнить итоговые ручные проверки из 04.4.7.
4. Сохранить открытыми подробную приёмку радара, удаление временного лога и восстановление проверки конфига в `TankRadarInstaller`; переход к GPS не означает их завершения.
5. Радиостанцию (04.4.5) реализовать после GPS, последней из модулей; далее выполнить общую приёмку 04.4.8 и оставшиеся подробные проверки ПНВ и радара.
6. Расход, заправку и влияние пустого бака на движение разбирать отдельно; готовый датчик не означает готовую топливную механику.
7. Продолжать небольшими шагами: объяснение, код и Inspector-инструкции; реализацию меняет пользователь. Документ можно обновлять по его запросу.
8. Различать проверку исходников/Inspector и подтверждение поведения в Play Mode; общую приёмку этапа 04.4 пока не закрывать.

Не считать весь этап завершённым по готовности одной камеры или нескольких тумблеров. Завершение требует согласованной функциональности всех включённых в объём устройств и финальной проверки панели.
